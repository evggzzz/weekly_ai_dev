GPT-6 Astra と Claude Fable 5.1 / Mythos 5.1 という2つの最上位モデルが、数日の間に揃って公開された一週間でした。
Codex CLI は Astra を即座にデフォルトモデルにし、GitHub Copilot CLI は claude-fable-5.1 に対応しています。モデルが増えること自体は歓迎すべきですが、その裏で ChatGPT・Claude・Grok が同時にダウンする障害が発生し、「どのプロバイダにどう依存しているか」を改めて問い直す必要に迫られました。
ツール側の動きは運用の安全境界に寄っています。Copilot CLI はサンドボックスからローカルホストへの到達を遮断し、Gemini CLI は Docker ソケットを macOS Seatbelt から分離し、Claude Code は使わないスキルのコンテキスト消費を見える化する `/skill-doctor` を追加しました。
研究面では、GitHub リポジトリを 5,000 以上の検証済みスキルに蒸留した Repo-To-Skill が MLE-bench 134.3% 向上を報告し、「スキルを配布する」設計の有効性が数字で示されています。

## 🚀 リリース情報

### Claude Code v2.1.261

使わなくなったスキルがコンテキストを圧迫する問題に対する機能が入りました。`/skill-doctor` を実行すると、読み込まれているスキルのうち未使用のものと、それぞれが消費しているコンテキスト量を確認できます。
出力をインラインで受け取る上限を引き上げる `bashOutputMaxChars` / `taskOutputMaxChars` 設定（最大 128K 文字）も追加され、長いコマンド出力をいちいちファイルで受け取る手間が減ります。
サブエージェントのシステムプロンプトをファイルから読む `--append-subagent-system-prompt-file` も加わり、CLI 引数に収まらない大きなプロンプトを扱えるようになりました。
`/status` と `claude doctor` には「Organization policy」行が追加され、組織ポリシーが読み込めない理由（プロキシがエンドポイントを通していない等）まで表示されます。
高速入力時の打鍵が入れ替わる・落ちる問題や、再開できないバックグラウンドエージェントが高 CPU のままリトライし続ける問題なども修正されています。

- リポジトリ: https://github.com/anthropics/claude-code
- CHANGELOG: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md

### GitHub Copilot CLI v1.0.83

claude-fable-5.1 モデルサポートの追加が目玉です。あわせてカスタムエージェントが `model` に複数モデルを列挙できるようになり、先頭から順に利用可否を試行します。`model-policy: required` を付けると、そのリストから外れるモデル変更を禁止できます。
サンドボックスの挙動が具体的に変わるリリースでもあります。macOS と Linux では、サンドボックス内コマンドがローカルホスト上のサービスへ到達できなくなりました。macOS ではコマンド自身が起動した 127.0.0.1 のサーバーも遮断されるため、ローカルポートを bind するテストスイートは失敗します。`/sandbox` の Allow local network で緩和できます。
サンドボックス内の `gh` コマンドは Copilot CLI のログインではなく、リポジトリに設定されたアカウントで認証されるようになりました。ファイルツールが `~/.npmrc` などトークンを含む開発ツールのパスを読めるようになった点は、`sandbox.allowDevToolAccess: false` で無効化できます。
Linux ではサンドボックスのネットワーク出口が設定済みプロキシに制限され、slirp4netns・util-linux 2.35 以上・iptables・/dev/net/tun が必要になります。
一時的なフォールバック後に Anthropic セッションが invalid thinking signatures で失敗せず継続する修正や、MCP OAuth の CIMD 対応、実行中セッションの Windows 11 タスクバー表示なども含まれています。

- リポジトリ: https://github.com/github/copilot-cli
- リリース: https://github.com/github/copilot-cli/releases/tag/v1.0.83

## 📈 注目のAI開発リポジトリ

https://github.com/MakazhanAlpamys/Soup

Soup は LLM のファインチューニングとポストトレーニングを 1 コマンドで行う CLI ツールです。「No SSH, no config hell」を掲げ、YAML を 1 枚書けば学習が回ります。
トレンドページの説明によれば、Layer streaming という方式で 8B モデルを 4GB のラップトップ GPU 上で学習できます。`pip install soup-cli` で導入でき、Apache-2.0 ライセンスです。

## 📄 今週のAI論文トレンド

### Repo-To-Skill: GitHub リポジトリを AI エージェント用スキルへ蒸留

自律エージェントが ML 研究をエンドツーエンドで行うようになった一方で、モデルのバックボーンとハーネスだけではドメイン固有のノウハウがエージェントの外に置き去りになっている、という問題設定から始まります。著者らはこの欠けた層を「operational knowledge（運用知識）」と呼びます。
提案する DisCo は、スキルを作り研究の中で使うエージェントです。蒸留は 2 形態で走ります。1 つはタスク非依存に分野の広く使われるリポジトリを再利用可能なスキルに凝縮する形、もう 1 つは具体タスクに必要なスキルを生成する形です。前者をオープンエコシステム全体に適用すると、広く使われる 1,000 の ML リポジトリから 5,000 以上の検証済みスキルを蒸留し、20 分野・178 の能力ファミリーに整理した AREX-Skill Library が得られます。
GPT-5.5 バックボーン・リサーチハーネス・実行予算を固定した比較で、スキルありのエージェントはスキルなしに比べ MLE-bench で 134.3%、PaperBench で 34.4%、FrontierCS で 9.2%、PassNet で 14.0% スコアが向上しました。
後付けの追加学習ではなく、蒸留された運用コンテキストの追加だけでこの差が出ています。Claude Code の Skills や Agent Plugins といった「スキルを配布する」設計の有効性を、大規模な実測で裏付けた研究と言えます。

- 著者: Jianlyu Chen, Yuyang Hu, Hongjin Qian, Jiawei Liu, Wenqing Wei, Xiaolong Chen, Defu Lian, Zhicheng Dou, Chaozhuo Li, Qiwei Ye, Zheng Liu
- arXiv: https://arxiv.org/abs/2609.02749

### Compile by Training: 自然言語の仕様をローカルのニューラル関数へコンパイル

繰り返し使うテキスト処理は、言葉で説明するのは簡単ですがルールで実装するのは難しい。入力のたびに大規模リモートモデルを呼ぶと、コスト・レイテンシ・プロバイダ依存が繰り返し発生します。
本論文の「compile by training」は、自然言語の仕様を再利用可能なニューラル関数にコンパイルする手法です。コンパイル時に教師モデルがタスク固有の例を生成し、それでコンパクトなインタプリタに小さなアダプタを学習させます。出来上がった関数は教師モデルなしで動き、通常のソフトウェアと同じように保存・バージョン管理・合成ができます。
FuzzyBench-Hard のうち先行の Program-as-Weights 高速コンパイラが 1 件も一致を出せなかったサブセットで、83.6% の意味的一致率に到達しました。精度と引き換えにコンパイル時間は秒単位から約 1 分に増えます。
公開の対話型サービスとして実装され、複数サイトのウェブヘルパー、言語操作できる 3D アバター、双方向の英〈Claudish〉翻訳器といった実例が示されています。「仕様を書いたらローカルで動く小さなモデル関数が得られる」方向は、推論コストとレイテンシが支配的なエージェント運用のあり方を変えうる提案です。

- 著者: Yuntian Deng, Pengyu Nie, Stuart Shieber
- arXiv: https://arxiv.org/abs/2609.04199

### HarnessDev: LLM は自らのエージェントハーネスを作り進化できるか

エージェントの実力がモデルの重みだけでなく、計画・実行・検証を担う「エージェントハーネス」に強く依存するようになった、という前提から始まります。しかし従来の評価は所与のハーネス下での下流タスク性能を報告するだけで、ハーネス自体を開発できるかはほぼ調べられてきませんでした。
提案する HarnessDev は評価の単位を「タスク出力」から「動くインフラ」に移すベンチマークです。Creation（最小シードと少数のケースから完全な実行システムを構築）と Evolution（自作ハーネスを下流の実行フィードバックで反復改良）の 2 段階で構成されます。
6 作成 LLM × 4 ドメイン × 5 下流ベンチマーク計 2,207 インスタンスの結果、生成ハーネスはコード系・検索研究系では成熟した人間製のリファレンスに大きく届かず、ライティングと ML 実験では同等以上になるなど大きくばらつきました。Evolution による改善は不安定で、未知タスクへの転移も部分的です。
実行モデルを固定した実験では、利得がハーネスを動かすモデルに強く依存し、モデルをまたぐ転移が限定的なことも分かりました。ハーネス設計は当面人間の仕事であり続けることを示す実測で、エージェント運用の「ツール定義・実行環境設計」に投資する価値を裏付けています。

- 著者: Yuhao Wu, Jingyuan Zhang, Jiajun Shi, Xinping Lei, Qingshui Gu, Yuxuan Zhang, Zexuan Wang, Chen He, Chen Huang, Maojia Song, Zhiyuan Zeng, Shaowen Wang, Jinkai Liu, Yunfeng Shi, Jiaheng Liu, Shen Yan, Wenhao Huang, Ge Zhang, Wenxuan Zhang
- arXiv: https://arxiv.org/abs/2609.01437
